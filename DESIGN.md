# AI-агент-консультант по академии селлеров Lamoda

Решение тестового задания: AI-агент, отвечающий на вопросы продавцов по
публичной базе знаний академии селлеров Lamoda (https://academy.lamoda.ru/).

Состоит из трёх частей:

1. **Парсер** — обходит academy.lamoda.ru и сохраняет статьи в Markdown
   (только текст) → `data/articles.jsonl`.
2. **Ретривер** — гибридный поиск (sparse **BM25** + dense **e5**) поверх
   собранных статей, всё **в памяти**, без внешних векторных БД. Интерфейс —
   `search_knowledge_base(query, k)`.
3. **ReAct-агент** — цикл «рассуждение → вызов инструмента → ответ» на чистом
   SDK провайдера (**Groq**), без LangGraph/Google ADK.

> Обоснования решений важнее идеальных метрик — поэтому они вынесены в
> markdown-ячейки ноутбука и в этот README.

## Файлы

- **`lamoda_seller_agent.ipynb`** — итоговый единый ноутбук (Части 1→2→3),
  запускается сверху вниз в Google Colab без ручных правок. **Это сдача.**
- `parser.ipynb` — только Часть 1 (парсер), для отдельного запуска/отладки.
- `retriever.ipynb` — Части 2–3 (ретривер + агент), для отдельного запуска.
- `data/articles.jsonl` — результат парсера (вход для ретривера).
- `README.md` — этот документ.

## Как запустить и проверить

1. Открой `lamoda_seller_agent.ipynb` в Google Colab.
2. (Опционально) Среда выполнения → **T4 GPU** — ускоряет расчёт эмбеддингов
   (на CPU тоже работает, просто дольше).
3. Для Части 3 нужен бесплатный API-ключ **Groq** (console.groq.com → *API Keys*).
   Ключ берётся из: переменной окружения `GROQ_API_KEY` → `AUTHOR_GROQ_KEY` в
   коде → ручного ввода в поле. Впиши свой ключ в `AUTHOR_GROQ_KEY` или введи при
   запуске — секрет в коде хранить не обязательно.
4. Среда выполнения → **Выполнить все**.

**Сигналы, что всё работает:**

| Часть | Что увидеть в выводе |
|---|---|
| 1 — парсер | сводка `найдено/сохранено/пропущено/упало`, **упало = 0**; создан `data/articles.jsonl` (~336 статей) |
| 2 — ретривер | `чанков ~2300`, `shape=(2307, 384)`, демо-запросы выдают top-K **со ссылками** на статьи |
| 3 — агент | в трейсе есть `Action: search_knowledge_base`, реальный вызов инструмента, `Final Answer` со ссылками на источники |

# Часть 1 — Парсер

Ниже — как устроен сайт, как мы это выяснили, какой подход выбран и почему, как
парсер оптимизирован, как он не падает на битых страницах и на каких краевых
случаях его надо проверять.

---

## 1. Как мы исследовали сайт (методология)

Прежде чем выбирать инструмент, мы эмпирически определили тип сайта и способ
доставки контента. Делать это «на глаз» нельзя — от ответа зависит весь стек
(нужен ли headless-браузер). Что мы проверяли и чем:

| Что проверяли | Инструмент / команда | Что выяснили |
|---|---|---|
| Тип сайта / платформа | `curl` + просмотр исходного HTML | 1C-Bitrix (`/bitrix/cache/`, `/local/templates/lamoda-academy/`) |
| Наличие карты сайта | `curl https://academy.lamoda.ru/sitemap.xml` | **404** — sitemap отсутствует, URL надо собирать самим |
| Правила обхода | `curl .../robots.txt` | `User-Agent: * / Allow: /` — обход публичной части разрешён |
| Есть ли тело статьи в HTML **без JS** | `curl` страницы → подсчёт видимого текста (`re` — снять `<script>/<style>/<tags>`) | Тело **листовых** статей присутствует в серверном HTML целиком |
| Тип страницы (раздел vs статья) | сравнение объёма видимого текста разных URL | Раздел-индекс ≈ 3.5 КБ (только меню), листовая статья ≈ 7+ КБ (с телом) |
| Структура контейнеров | `re`-поиск классов вокруг `<h1>` и текста | тело в `div.article-detail-content` → `article-detail-text` |
| Догрузка через AJAX | поиск `fetch(`, `$.ajax`, `data-url`, `iframe` в HTML | Контент тела **не** догружается AJAX; JS дорисовывает только оглавление (`#pointers`) |

**Ключевые находки:**

1. Сайт на **1C-Bitrix**, контент статически рендерится сервером.
2. **`sitemap.xml` отсутствует** → ссылки нужно собирать из навигации.
3. **Тело листовых статей есть в HTML без JS** → headless-браузер не нужен.
4. Есть **два типа страниц**:
   - *разделы-индексы* (`/articles/api/`, `…/osnovnaya-informatsiya/`) —
     только список подстатей, тела нет;
   - *листовые статьи* (`…/sertifikat-sootvetstviya/`) — с `<h1>`, телом,
     датой «Обновлено» и блоком «Помогла эта информация?».
5. **Полное дерево навигации** (все URL `/articles/...`) встроено в сайдбар
   **каждой** страницы → обнаружение ссылок тривиально, глубокий обход не нужен.
6. Селекторы контента:
   - тело — `div.article-detail-content` → `article-detail-text`;
   - заголовок — `<h1>`;
   - дата обновления — `.article-detail-date__value`;
   - конец тела (маркер) — `.article-feedback` («Помогла эта информация?»);
   - путь категории — `breadcrumb`.

## 2. Выбор подхода и обоснование

Главный архитектурный вопрос — **нужен ли рендеринг JavaScript**. Мы проверили
эмпирически (см. раздел 1): тело статей уже в серверном HTML, поэтому
**headless-браузер избыточен**. Это решающий фактор для скорости и стабильности
в Google Colab.

| Подход | Скорость | Стабильность в Colab | Вывод |
|---|---|---|---|
| **Playwright / Selenium** (headless) | Медленно (старт браузера, рендер страницы) | Требует `playwright install chromium` (~300 МБ), часто нестабилен в Colab | ❌ Избыточно — контент и так в HTML |
| **Scrapy** | Быстро | Свой реактор/процесс конфликтует с event-loop ноутбука | ❌ Тяжёлый фреймворк ради одной задачи |
| **requests + BeautifulSoup** (`html.parser`) | Средне | Стабильно | ⚠️ Медленный парсинг на сотне+ страниц |
| **httpx (async) + selectolax + обход дерева** | Быстро (конкурентность + C-парсер) | Чистый Python, без бинарей | ✅ **Выбор** |

**Итоговый стек:** `httpx` (async, HTTP/2, пул соединений) + `selectolax`
(парсер на движке Lexbor, в разы быстрее BS4/lxml) + ручная конвертация в
Markdown.

**Почему именно так:**

- Контент статический → узкое место — сетевой I/O, а не рендер/CPU →
  решается **асинхронной конкурентностью** (10–16 параллельных запросов с
  семафором), а не браузером.
- `selectolax` даёт CSS-селекторы и устойчив к «грязному» HTML (у Bitrix-вёрстки
  незакрытые теги — обычное дело; strict-режим lxml на этом падает).
- Нет внешних бинарей → воспроизводимость: ноутбук «запускается сверху вниз без
  ручных правок» (критерий готовности).

**Фолбэк для надёжности в Colab:** если установка `selectolax` по какой-то
причине не проходит, ноутбук автоматически переключается на
`requests` + `BeautifulSoup(html.parser)` — те же селекторы, чуть медленнее.

## 3. Алгоритм работы парсера

1. **Discovery (сбор URL).** Рекурсивный обход всего сайта не нужен: полное
   дерево `/articles/...` лежит в сайдбаре. Берём `GET /`, вытаскиваем все
   `href^="/articles/"`, нормализуем (абсолютный URL, убираем якоря/query,
   единый trailing-slash), дедуплицируем. Для подстраховки — лёгкий BFS на
   1–2 уровня вглубь (на случай статей, не попавших в меню).
2. **Классификация страниц.** Лист (сохраняем) vs раздел (тело пропускаем)
   определяем по наличию `article-detail-text` **и** блока `.article-feedback`
   при непустом `<h1>`. Разделы всё равно служат источником новых ссылок.
3. **Извлечение.** Из листа берём: `<h1>` (заголовок), breadcrumbs
   (категория/путь), дату «Обновлено», тело `article-detail-text`.
   **Чистим обвязку:** сайдбар-меню, cookie-баннер, блок «Помогла эта
   информация?», «популярные статьи», `<script>/<style>`.
4. **HTML → Markdown.** Конвертируем `h1–h4`, `p`, `ul/ol/li`, `table`,
   `a[href]` (ссылки — в абсолютные). Изображения сводим к alt-тексту/подписи
   (по заданию — «только текст»). Нормализуем пробелы и переводы строк.
5. **Сохранение.** Один `.md` на статью + YAML-фронтматтер
   (`url`, `title`, `breadcrumbs`, `updated`, `slug`). Имя файла — из slug пути.
   Параллельно пишем `articles.jsonl` — удобный вход для ретривера.

---

## 4. Оптимизация

- **Async + семафор** (concurrency ≈ 10–16) — основной ускоритель (сеть — узкое
  место).
- **Пул соединений / keep-alive**, HTTP/2 в `httpx`.
- **Дисковый кеш сырого HTML** (по хешу URL): повторный прогон ноутбука не бьёт
  по сайту и проходит за секунды.
- **Вежливость:** корректный User-Agent, джиттер между запросами, ограничение
  rps (robots.txt разрешает обход).
- `selectolax` вместо BS4 — снимает CPU-затык на сотне+ страниц.

---

## 5. Устойчивость («не падает на одной битой странице»)

Это явный критерий готовности задания.

- Каждый URL обрабатывается **изолированно** в `try/except`; ошибка логируется и
  **не роняет** весь прогон.
- **Таймауты** (connect/read) + **ретраи с экспоненциальным backoff** на
  429/5xx/сетевых сбоях; 404/403 — скип с пометкой.
- **Валидация результата:** пустой `<h1>` или пустое тело → статья помечается
  `skipped`, а не пишется битый `.md`.
- Финальный **отчёт**: найдено / сохранено / пропущено / упало — со списком
  проблемных URL.

---

## 6. Краевые случаи — где парсер может сломаться (обязательно проверить)

1. **Страница-раздел без тела** — не принять список подстатей за статью
   (ложно-пустой `.md`). → классификатор по `article-detail-text` + `feedback`.
2. **Битый/незакрытый HTML** Bitrix — `selectolax` и BS4 `html.parser` терпят;
   strict-lxml — нет.
3. **Дубли URL** (со слешем/без, с query, регистр) — нормализация до дедупа.
4. **Циклы в навигации / бесконечный обход** — множество `visited` + лимит
   глубины.
5. **Редиректы и trailing-slash** — `follow_redirects=True` + нормализация.
6. **Очень большие статьи / таблицы** (API-спека: `apispec`,
   `api-specification-lamoda-seller-rest`) — таблицы и `<pre>` не должны ломать
   MD-конвертер; проверить именно эти страницы.
7. **Контент, дорисовываемый JS** (`#pointers` «Содержание статьи» пуст в HTML)
   — игнорируем; тело берём из server-HTML; убедиться, что текст не теряется.
8. **Не-статейный контент** (баннеры, FAQ-аккордеоны) — проверить, что текст
   внутри аккордеонов есть в HTML, а не подгружается AJAX.
9. **Кодировка** (UTF-8, кириллица) — явно выставить; проверить отсутствие
   mojibake.
10. **429 / троттлинг** при высокой конкурентности — backoff + лимит rps.
11. **Пустые/технические страницы** (`podderzhka`, `ustoychivoe-razvitie`) —
    валидация на минимальную длину тела.
12. **Смена вёрстки** (классы изменятся) — селекторы вынести в конфиг + фолбэк
    «брать самый крупный текстовый блок», чтобы парсер деградировал мягко, а не
    падал.

**Набор тестов.** Разметить вручную 4–5 эталонных URL и проверить:

| URL-тип | Пример | Ожидаемо |
|---|---|---|
| Обычная листовая статья | `…/certification/osnovnaya-informatsiya/sertifikat-sootvetstviya/` | Непустой MD с заголовками |
| Статья с таблицей / API-спека | `/articles/api/api-specification-lamoda-seller-rest/` | Валидный MD, таблицы не ломают конвертер |
| Раздел-индекс | `/articles/api/` | НЕ сохраняется как статья |
| Несуществующая страница | любой `/articles/нет-такой/` | Грейсфул-скип (404), прогон продолжается |
| «Тонкая» страница | `/articles/podderzhka/` | Скип по валидации длины |

Критерий прохождения: счётчики отчёта (найдено/сохранено/пропущено/упало)
сходятся, прогон не прерывается ни на одной странице.

# Часть 2 — Ретривер

Гибридный поиск поверх собранных статей. Всё работает **в памяти ноутбука**, без
внешних векторных БД и сервисов (Qdrant, pgvector, FAISS-server) — требование
задания.

## Архитектура и обоснование

| Слой | Что | Зачем |
|---|---|---|
| Чанкинг | разбиение статьи по заголовкам **H2/H3** + overlap | заголовок — естественная смысловая граница; чанк влезает в контекст и точно цитируется (url + раздел) |
| Sparse | **BM25** по лемматизированным токенам (`pymorphy3`) | ловит точные термины: коды, `FBO`, `API`, имена полей — там, где эмбеддинг «размывает» |
| Dense | **intfloat/multilingual-e5-small** (косинус) | ловит перефраз/синонимы; e5 силён на русском; small быстро считается на CPU |
| Fusion | **RRF** (Reciprocal Rank Fusion) | у BM25 и косинуса несравнимые шкалы; RRF работает по рангам — без подбора весов, устойчиво |
| Выдача | top-K чанков + URL источника | критерий задания: результат с указанием источника |

**Почему именно так:**

- **Чанкинг по H2/H3.** Статью целиком класть в индекс плохо: длинный текст
  «усредняет» эмбеддинг. Режем по авторским заголовкам; длинные блоки (таблицы)
  добиваем по строкам, чтобы чанк не превышал лимит и не обрезался моделью.
  Каждый чанк несёт метаданные (`url`, `title`, `breadcrumbs`) — иначе нельзя
  сослаться на источник.
- **Гибрид sparse + dense.** Лексический BM25 и семантический e5 закрывают слабые
  места друг друга: точные термины/коды берёт BM25, перефраз и синонимы — e5.
- **RRF вместо сложения баллов.** Шкалы BM25 (неограниченная) и косинуса (`[-1,1]`)
  несравнимы. RRF суммирует `1/(k+rank)` по рангам — устойчиво и без подбора весов
  (`k = 60`, стандартное значение).
- **e5-small, а не base.** На корпусе ~2.3 тыс. чанков качество почти не отличается,
  зато считается на CPU за минуты — ноутбук не требует GPU.
- **Кеш эмбеддингов** на диск (`data/emb_*.npy`): повторный запуск не пересчитывает.
- **Косинус = dot** на L2-нормированных векторах → быстрый матричный поиск через
  numpy, без FAISS/внешней БД.

## Интерфейс

`search_knowledge_base(query, k=5)` → список из `k` фрагментов с полями
`text, title, url, breadcrumbs, heading, score`. Эта же функция — инструмент
агента в Части 3.

## Что можно улучшить

- **Реранкер** (cross-encoder, напр. `bge-reranker`) поверх top-N RRF.
- **Взвешенный RRF** под тип запроса (короткий код vs длинный вопрос).
- **Семантический чанкинг** для статей без чёткой структуры H2/H3.
- **Метаданные в скоринг**: бустить чанки из релевантного раздела или свежие.

# Часть 3 — ReAct-агент

Агент-консультант: отвечает на вопросы продавцов, **сам решая**, когда обратиться
к базе знаний. Цикл **ReAct** реализован вручную на чистом SDK провайдера
(**Groq**), без LangGraph/Google ADK.

## Как работает

Цикл: **Thought** (рассуждение) → **Action: search_knowledge_base: <запрос>** →
**Observation** (фрагменты из ретривера) → … → **Final Answer** (ответ + URL
источников). Протокол задаётся системным промптом; ответ модели парсится
регулярками; при `Action` реально вызывается `search_knowledge_base`. Число шагов
ограничено (`max_steps`) — защита от зацикливания.

## Решения и обоснование

- **Провайдер Groq** — бесплатный ключ без карты, OpenAI-совместимый API, модель
  Llama 3.3 70B (хорошо знает русский).
- **Ручной ReAct, а не нативный function-calling** — требование задания «без
  фреймворков»; плюс код становится **провайдеро-независимым**: при смене LLM
  меняется только обёртка `llm_call` (~10 строк).
- **Защита от галлюцинаций** — системный промпт требует брать факты только из
  `Observation`, указывать URL источников и сделать минимум один поиск перед
  ответом.

## Ключ Groq

`AUTHOR_GROQ_KEY` в ячейке подключения — слот для ключа автора. Источники по
приоритету: env `GROQ_API_KEY` → `AUTHOR_GROQ_KEY` → ручной ввод. Проверяющий
может запустить со своим ключом или с приложенным.

## Что можно улучшить

- **Нативный function-calling** провайдера вместо текстового парсинга `Action:`.
- **Несколько инструментов** (поиск по разделу, уточняющий вопрос пользователю).
- **Память диалога** между вопросами.
- **Guardrails**: пост-проверка, что все факты ответа подкреплены источниками.
